# 与 AI 协作的工作流

本章写给人看，讲在 vibe coding 项目里怎样和 AI 编码助手（agent）一起工作。[AGENTS.md](../AGENTS.md) 规定 AI 应该怎么做；本章讲你这一侧该做什么：什么时候拍板、看什么、怎么验收、哪些坑要避开。

两份文件是配套的。AGENTS.md 里每一条对 AI 的要求，背后都有一个需要你配合的动作。如果你发现 AI 没有按 AGENTS.md 做，直接指出来，让它回到规则上。

## 1. 先摆正角色

- **你是产品经理兼技术负责人。** 你决定做什么、做到什么程度、什么算完成。AI 负责把它做出来，并把过程讲清楚。
- **AI 是能干但会自信犯错的同事。** 它写得快，但会误解需求、编造不存在的 API、为了让测试通过而改测试。它说"完成了"，不等于真的完成了。
- **你不需要读懂每一行代码，但要能验证结果。** 验证靠的是：清楚的设计说明、能跑的测试、能看到的运行效果。这正是 AGENTS.md 要求 AI 提供这些东西的原因。

## 2. 一个功能的完整流程

```
提出需求 → 对齐设计 → 开发与自测 → 提交 PR 与 review → 验收合并 → 部署 → 维护
              ↑ 你确认                      ↑ 你看结论        ↑ 你验收
```

### 2.1 提出需求

讲清楚三件事就够了：

1. **要解决什么问题**，给谁用。
2. **怎样算做完**：一两个具体场景，例如"用户上传 CSV 后，能在列表里看到导入的记录，格式错误的行会单独提示"。
3. **约束**：不能动的部分、必须用的服务、时间和成本限制。

不需要一开始就想得很完整。说不清的地方，让 AI 先提问，或者先给几个方案让你选。

### 2.2 对齐设计（最重要的一步）

按 AGENTS.md，AI 在写代码前应该先给你讲清楚：

- 功能和业务流程，配简单流程图
- 数据结构，以及数据之间的关系

**你的任务是认真看这一步，并明确回复"确认"或"要改"。** 这一步改一句话的成本，到写完代码后可能变成改一天。检查时可以问自己：

- 流程图里的每一步，是不是我真正想要的业务流程？有没有漏掉异常情况（失败、重复提交、权限不足）？
- 数据之间的关系对吗？例如一个用户能不能有多个账户，删除一条记录时相关数据怎么处理。
- 用的术语和我平时说的是不是同一个意思？如果不是，现在就统一。AGENTS.md 要求术语只定义一次，全项目通用。
- 核心模块以后要扩展的方向，设计里有没有留余地？

如果 AI 跳过设计直接写代码，叫停它，要求先补设计。

### 2.3 开发与自测

这一段主要是 AI 在干活。你不需要盯着，但要知道它应该交出什么：

- **两层测试**：底层功能测试，加上端到端的用户场景测试。
- **覆盖关键流程和边界情况**，覆盖率尽量 100%；达不到时，AI 应该说明原因并提出可行目标。
- **外部依赖都有保护**：超时、有限重试、熔断，失败要能看到，不能静默吞掉。

中途 AI 来问你问题时，尽量及时回答。它卡住时常常会自己"猜一个"继续做，猜错的代价比等你回答更高。

### 2.4 PR 与 review 循环

AGENTS.md 规定的循环是：

1. AI 提交 PR 前先自己复查一遍。
2. 提交后自动申请 GitHub Copilot review，按意见修改，再申请。
3. 满足任一条件就停：Copilot 不再提新意见，或者已经满 7 轮。
4. 同一处代码因为 review 反复改超过 3 次，先停下来检查设计是否有问题。

**你在这个循环里看什么：**

- **看结论，不看过程。** 让 AI 用通俗语言总结：这个 PR 做了什么、改了哪些行为、测试覆盖了哪些场景、还有什么没做。
- **看 review 意见有没有被认真处理。** AI 拒绝某条意见是可以的，但要有理由。
- **注意"反复改同一处"的信号。** 如果 AI 告诉你某处已经改了三轮还没稳定，这通常说明设计有问题，而不是代码没写好。这时回到 2.2，重新讨论设计。

### 2.5 验收与合并

合并前，你至少亲手做一次：

- 按 2.1 里写的"怎样算做完"场景，自己走一遍（在 staging 或本地）。
- 确认 CI 是绿的，测试真的跑了，没有被跳过或删掉。
- 看一眼 PR 描述里"没做的事"和"已知问题"，决定能不能接受。

合并是你的决定，不是 AI 的。

### 2.6 部署

AGENTS.md 对环境的要求，你需要在项目早期就和 AI 一起落实：

- staging 从零搭建，不复制生产环境。
- staging 和生产跑同一份代码，靠独立的凭证、数据库、存储桶、队列隔离，而不是靠代码里的开关。
- 非生产环境的页面都显示当前环境名。

**凭证和生产操作由你掌控。** 不要把生产环境的密钥直接交给 AI 会话；涉及生产的改动（数据迁移、删除数据、改 DNS）要求 AI 先说明影响，你确认后再执行。

### 2.7 维护

程序完成后，要求 AI 给你一套维护方案，包括怎样用 agent 或定时任务（routine）自动打功能补丁和安全补丁。拿到后检查：

- 方案是否简单到你自己能看懂、能执行？
- 出问题时谁会收到通知？

出故障时，AI 应该先告诉你三件事：影响多大、大致原因、能否快速修好。严重影响生产又修不快时，先要临时方案恢复服务，再要完整方案。你可以直接用这三个问题去问它。

## 3. 怎么和 AI 说话

- **一次说一件事。** 一条消息里塞五个需求，AI 容易漏掉或者混在一起做。
- **给例子，而不是只给形容词。** "界面要简洁"不如"参考 X 页面的布局，只保留搜索框和结果列表"。
- **说清楚不要什么。** "不要改数据库结构""不要引入新的依赖"这类约束很有用。
- **要求它复述。** 复杂需求讲完后，让 AI 用自己的话复述一遍，再开始做。
- **纠正时说原因。** "这样不对，因为我们的用户大多在手机上用"比"这样不对"更能让 AI 举一反三。
- **把长期规则写进 AGENTS.md。** 同一句话说了三遍，就该写进规则文件，而不是每次都重复。

## 4. 常见的坑

| 坑 | 表现 | 怎么避免 |
| --- | --- | --- |
| 跳过设计 | AI 一上来就写代码，写完才发现方向不对 | 坚持先看流程图和数据结构，确认后再开工 |
| "完成了"但没验证 | AI 说做完了，实际跑不起来或者只做了一半 | 按验收场景亲手走一遍，看测试是否真的跑了 |
| 改测试迁就代码 | 测试失败时，AI 修改或删除测试让它通过 | review 时留意测试文件的删除和断言的放宽 |
| 用过时的知识 | 用了旧版本运行时、废弃的 API 或旧默认值 | 要求以官方文档为准；运行时用当前 LTS |
| 编造 API 或配置 | 调用了不存在的函数或参数 | 让 AI 给出官方文档链接；测试必须真实跑通 |
| 静默失败 | 外部服务出错时程序不报错，数据悄悄丢了 | 检查超时、重试、熔断和错误可见性 |
| 在一个方向死磕 | 同一个 bug 改了很多轮还在反复 | 超过 3 次就停下来，重新审视设计 |
| 术语漂移 | 同一个概念在代码、界面、文档里叫不同名字 | 设计阶段统一术语，写进文档 |
| 上下文丢失 | 会话变长或换了会话后，AI 忘了之前的决定 | 重要决定写进 AGENTS.md 或项目文档，不只留在聊天里 |
| 范围蔓延 | AI 顺手"优化"了你没要求的部分 | 一个 PR 只做一件事，要求 PR 描述列出所有行为变化 |
| 生产事故 | AI 直接对生产环境执行了不可逆操作 | 生产凭证不交给 AI；不可逆操作必须先确认 |

## 5. 一页速查

开工前：

- [ ] 我讲清楚了问题、完成标准和约束
- [ ] 我看过并确认了流程图和数据结构
- [ ] 术语已统一

合并前：

- [ ] 我读过 PR 的通俗总结，包括没做的事
- [ ] 两层测试都在，CI 是绿的，没有测试被删除或跳过
- [ ] Copilot review 循环已结束（无新意见或满 7 轮）
- [ ] 我亲手走过一遍验收场景

上线与维护：

- [ ] staging 独立搭建，页面显示环境名
- [ ] 生产操作经过我确认
- [ ] 维护方案我能看懂、能执行
